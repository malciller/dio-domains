The DIO Capital Oracle: What It Is
The oracle is a capital-survival sizing engine for the grid-trading strategy. The question it answers for each asset:
"Given this asset's real price history and the quote capital available on its exchange account, what order size (qty) and grid interval (gi) should the grid run at, so that it survives the worst drawdowns this asset has actually experienced? The sizing targets 100% replay survival over the whole history; the statistical target (99% by default) drives the governing-drawdown basis and the maturity warnings."

It runs in two places:
1. bin/oracle.ml, the dio-oracle CLI. It is a one-shot tool: fetch history, analyze, print the report.
2. oracle_runtime.ml, inside the live engine. It runs a continuous loop that re-analyzes roughly every 5 minutes and publishes decisions the trading domains adopt. The live runtime is managed by the supervisor like every other engine module (Supervisor.start_oracle). It is registered in the connection registry as "oracle", started through the standard lifecycle machinery, heartbeated on every published pass plus a 10s liveness ticker, and auto-restarted by the health monitor if its loop ever dies. On engine shutdown the supervisor stops it with the rest of the modules.

The core statistical idea is MFD, Maximum Fractional Drawdown: over a window of h sessions, how deep did the price fall from the session-start close?
MFD(s, h) = 1 − (min low over sessions (s, s+h]) / close at s
F_h(d)    = P(MFD_h ≤ d)     is "coverage" (a CDF)
S_h(d)    = 1 − F_h(d)        is "survival"
The oracle computes these empirically from the asset's own history, blends them with a risk-class prior (pooled histories of "similar" assets) via a kappa-weighted, volatility-normalized blend, then inverts the blended CDF to find the governing drawdown at the statistical target. Finally it sizes the grid ladder so its capital runway survives the whole replayed history (the tightest config interval reaching 100% replay survival at the minimum order size, qty grown behind 100% survival to deploy the pool, or the stretch sizing when 100% is unreachable), replaying the strategy over the historical path to verify.

1. Data Layer
oracle_types.ml: shared types. bar, series, gap, horizon, survival_surface, percentile_table, blended_surface, sizing_result, range_stats, deployment_row, asset_deployment, plus calendar_kind (Crypto = 24/7 days; Equity = market sessions).

oracle_calendar.ml: session-consistent time handling.
- Pure civil-date arithmetic (days-from-epoch, Hinnant's algorithms). It avoids mktime, which is timezone-dependent and corrupted equity gap detection.
- Sorts bars by ISO date and de-duplicates.
- Gap detection: for crypto, any calendar day without a bar is a gap; for equity, a weekday missing from the expected-session model (US weekdays minus holidays, from Alpaca's calendar) is a gap.
- The "never forward-fill" rule: gaps are surfaced as metadata; Oracle.analyze refuses to analyze if max_gap > tolerance (default 5). Missing data is never fabricated.

oracle_sessions.ml: expected-session models for equities. business_weekday (Mon-Fri), explicit_model (exact date set), alpaca_model (weekday and in calendar), with_holidays. Pure math.

oracle_fetch.ml: the shared registry-driven series pipeline used by both the runtime and the CLI (venue dispatch through Exchange_intf.Oracle.Registry, disk cache, central clean-series normalization, Yahoo deep history, equity session calendar). Each venue has one historical-data adapter implementing Exchange_intf.Oracle.S: kraken_oracle.ml, hyperliquid_oracle.ml, alpaca_oracle.ml.
- Kraken: public /0/public/OHLC, paginated on last back to the pair's inception (each page ~720 candles, 60-page bound).
- Hyperliquid: /info candleSnapshot. It resolves spot vs perpetual: a bare coin name means perpetual, BASE/QUOTE maps through the spotMeta universe to the candle coin (@N alias or PURR/USDC). A spot-named symbol with no matching pair gets no bars and is marked inactive; it is never silently substituted with perp data. The response is normalized at the source (Oracle_calendar.normalize_bars, applied on every fetch read and cache read so runtime, CLI and replay share one series). candleSnapshot emits fabricated rows for wrapped spot pairs: pre-listing placeholder candles with constant dummy OHLC and zero/dust volume (UBTC/USDC: 6,969,696 / 7,979,573 on 2025-02-03..2025-02-13, which read as a phantom 99.3% drawdown and a $7.98M "peak"), plus rows whose extreme prints never traded (open/high 240,000 on a day closing 97,578). Rows with non-finite/non-positive fields or an impossible >10x single-candle range are dropped; rows whose extreme prints sit >2x off the row's own close are folded into the close (the day's real level survives, no fabricated peak/valley); rows whose close deviates >8x from the nearest real-trading neighbor (left first, then right; real = volume >= 0.01) are dropped. The judge is local, never a global median: a series that genuinely 100x'd (BTC ~$1k in 2017 vs ~$40k now, ETH ~$90 in late 2018) must keep its cheap-era rows; only rows ~100x off the market around them (fabricated placeholder levels) are dropped. A zero-volume carried price near the market survives, and a series with no real-volume row at all normalizes to empty and is marked inactive, never producing a garbage decision.
- Alpaca: /v2/stocks/{symbol}/bars (IEX/SIP) plus /v2/calendar for session dates.
- Yahoo (src/external/yahoo/yahoo_deep_history.ml, [dio.yahoo]): deep-history extension. Venue feeds cap history (~720 days Kraken, 2020 Alpaca IEX), so for the same underlying asset it fetches full daily history from Yahoo and prepends it (venue bars win on overlap; nothing synthesized). Crypto symbols only via an explicit whitelist (dead-token collision safety, e.g. HYPE-USD serves a dead 2021 token's prices). Windows Yahoo reports as pre-listing ("Data doesn't exist") are skipped rather than aborting the walk, and the confirmed-empty prefix is cached per symbol: a recently-listed asset (SPCX) contributes its empty range once and is never re-requested on every pass. The client lives outside the oracle (a leaf library depending only on dio.exchange for the shared bar/date helpers) and is consumed by oracle_fetch.ml.

oracle_fees.ml: resolves real maker/taker fees per venue (Kraken TradeVolume tier, Hyperliquid userFees, Alpaca = 0). An explicit maker_fee in config wins; fetch failures fall back to venue defaults; cached per (exchange, symbol). Both fee calls are timeout-guarded (5s), so a hung fee endpoint cannot freeze a pass. Venue-specific fee data lives only in the adapters (default_fees); this module keeps a single generic last-resort constant for unregistered (pure/offline/test) venues.

HTTP is never shared: each external client (venue adapters, the Yahoo library) owns its own timeout-bounded request wrapper (Lwt_unix.with_timeout). A blackholed upstream raises and the caller's failure handling applies (warn + fall back, or return what it has). The runtime additionally bounds each asset's whole analysis at 60s (last-known-good on timeout), so even a future fetch that forgets its timeout cannot freeze the pass.

oracle_venues.ml: venue instrument metadata (price ticks, lot sizes) fetched once from each exchange, so the replay uses real increments, not the 0.01 fallback. The metadata init dispatches through Exchange_intf.Oracle.Registry; venue registration is owned by the binaries (bin/main.ml / bin/oracle.ml force-reference the venue impl modules, whose load-time side effects populate both registries, because OCaml dead-code elimination would otherwise skip them).

oracle_balances.ml: account balance snapshots with two sources. The live runtime prefers the engine's websocket-fed balance stores, with REST as the fallback. Whether a venue has a WS-fed live store, and whether its semantics match the oracle's REST balance view, is the venue's answer (Exchange_intf.Oracle.S.live_balances): Kraken (authenticated WS feed) and Alpaca (account/positions feed) return their store; Hyperliquid returns None (the live store aggregates perp clearinghouse USDC into the same entry as spot, while the oracle's pool counts spot only), keeping REST spot spotClearinghouseState authoritative. The snapshot also feeds the sizing's accumulated-state seed (available base per asset).

oracle_tasks.ml: resolves CLI symbol/--exchange into analysis tasks (or all config.json trading entries). It maps exchange to calendar kind. oracle_loader.ml: offline CSV/JSON fixture loading.

grid_adapter.ml: bridges a config.json trading_config into a Grid_core.config for replay. Increments come from the venue registry, min_notional resolves through the venue's oracle adapter (Exchange_intf.Oracle.S.min_notional: Hyperliquid spot = 10 USDC floor, others 0), plus the exchange model.

2. Statistical Core
oracle_math.ml: dependency-free helpers.
- percentile (Type-7 linear interpolation) and weighted_percentile (the same estimator with weights; it reduces exactly to the unweighted version with unit weights). Both raise on empty input: an empty distribution must never masquerade as "this asset never drew down".
  - range_stats_of: per-asset ATH / all-time low / current price / d_from_ath / d_to_low / range_span. Context for the ATH-scaled survival reference. The ATH is the regime anchor; the ATH-to-ATL span itself is never the sizing drawdown, since a 1000x run-up would make it read like a 99.9% drawdown.
  - peak_to_valley_stats_of: the deepest actual peak-to-valley drawdown of the (deepened) history. Each bar's fall from the running peak of closes down to that bar's low, maximized, with the peak/valley prices and dates, plus a `recovered` flag (a later close >= the peak means the downtrend ended in recovery). Returns None only when the history is empty or strictly monotone (never drew down).
  - floor_overshoot_p90_of: measured floor-break history. A floor is a bottom that held and bounced; a floor break is a later low below it, (floor − breach)/floor. Only breaks followed by recovery count. The 90th percentile funds the at-floor / unrecovered regimes. Returns None (0.15 fallback) when no recovered break was ever measured.
  - sizing_reference_of / sizing_drawdown_of: the ATH-scaled survival reference (see §4). floor_ref = ATH·(1 − max_drawdown); above the floor, fund the remaining drop (price − floor_ref)/price, which never exceeds the worst-ever drop; at/below the floor ("living in the max drawdown") or with an unrecovered deepest event, fund the measured 90th-pct floor overshoot. Immature fallback assets keep the raw event drawdown.

oracle_mfd.ml: the MFD machinery.
- mfd: rejects incomplete windows (which would silently bias the CDF toward smaller drawdowns), non-finite/non-positive closes, and zero horizons.
- f_h / survival / n_starts / samples: empirical CDF machinery over starts in [warmup, n−horizon−1]. The stride parameter matters: stride = horizon gives non-overlapping windows (independent observations); stride 1 gives overlapping ones (autocorrelated). Percentile tables are estimated on non-overlapping windows so one contiguous crash is not counted once per rolling start. n_eff reports the true independent count (a 365-day horizon on ~1600 sessions yields only ~4 independent windows; P99 is then "the worst of those", which is the honest answer).
- surface / percentile_table: per-horizon output rows.
- Static runway math: the closed-form ladder cost C_used(N) = (1+fee)·q·C_s·(1−gi)·(1−(1−gi)^N)/gi and floor_aware_runway_cost, a walk of the actual ladder that replicates Grid_core's rounding and dynamic buy up-sizing (q_k = max(qty, ceil_lot(min_notional/level_k))). The closed form understates cost when the venue's notional floor binds.

oracle_stats.ml: the no-lookahead invariant. Trailing volatility at start s uses only closes from [s−W, s]. z(s,h) = MFD(s,h) / (σ_s·√h) is the volatility-normalized drawdown. blend is the kappa pseudocount: F_blend = (n_a·F_asset + κ·F_class)/(n_a + κ).

oracle_archetypes.ml: the risk-class data model (crypto_core, crypto_alt, equity_etf, equity_momentum) with default kappa = 365 (crypto) / 252 (equity), one per-session "prior weight" per full year of class history.

oracle_classes.ml: pooled class curves (Phase 2).
- Membership comes from config.json's "classes" map, never hardcoded.
- pooled: all members' per-start MFD samples pooled with either session-count weighting (longer histories dominate) or equal weight per member.
- class_surface / class_percentile_table: the class's own CDF/percentile tables over the pooled samples.
- z_index_of / z_cdf_of: the pooled class z-distribution (sorted weighted z-samples with prefix sums, O(log n) evaluation). This is what makes the blend vol-fair: the class contribution is evaluated at each asset start's own volatility regime, so a low-vol asset is not punished for a high-vol classmate's raw swing size.

oracle.ml: the facade.
- analyze: sort/dedup bars, detect gaps, fail-fast if max_gap > tolerance, then compute per-horizon surfaces, percentile tables, and per-class estimates plus blended surfaces/tables.
- default_config: crypto horizons [30; 90; 180; 365] days, equity [21; 63; 126; 252] sessions; thresholds 5-50%; percentiles 50-99%; vol_window 60; gap_tolerance 5.
- blended_percentile_table: inverts the z-blend CDF per percentile via bisection (the blend is monotone in d, so bisection is exact on the empirical step function).

3. The Blend Model (oracle_replay.ml)
The heart of the model. For one (asset, horizon, stride-basis):
F_asset(d)     = share of the asset's own windows with MFD ≤ d     (raw CDF)
F_class_avg(d) = (1/n)·Σ_s  F_class^z( d / (σ_s·√h) )
                 (pooled class z-CDF evaluated at each asset start's own vol)
F_blend(d)     = (n_a·F_asset(d) + κ·F_class_avg(d)) / (n_a + κ)

Key details:
- stride defaults to the horizon (non-overlapping windows) for every coverage evaluation: sizing inversion, surfaces, and percentile tables all share one consistent basis.
- n_asset is the window count on that same basis, so κ is a true pseudocount against the asset's effective independent sample size. A thin non-overlapping sample shrinks toward the class instead of pretending overlapping starts are independent information.
- Sigma = 0 (flat/gap-adjacent) windows are excluded from both sides. Mapping them to τ = +∞ would inject false 100% class certainty; keeping them only in F_asset would make an inconsistent weighted average.
- All three are monotone non-decreasing in d, so bisection is sound (explicitly noted because replay D_surv is not monotone in capital).
d_for_coverage: bisection over d ∈ (0, 0.999999) to find the smallest drawdown whose coverage reaches target; 40 iterations ≈ machine precision. The cap at 0.999999 protects fills_for_drawdown's log from saturation. Callers re-check achieved coverage because the cap can sit in the gap between "deepest exhausting coverage" and "never-exhausted 1.0".

Sizing functor (strategy-generic inversions, instantiated over Oracle_strategy.Grid):
- find_min_capital: the smallest capital whose static runway survives the ATH-scaled survival reference (see §4; mature assets: the remaining drop to the expected floor, or the measured floor overshoot at/below it). The static runway is the closed-form worst case (N consecutive buys, no sells), structurally pessimistic, so this is the safe recommendation.
- max_qty: the largest qty the grid's start_quote budget can fund through the actual max drawdown (exponential growth + bisection; exact under floor-aware cost).
- empirical_min_capital: advisory. The smallest capital whose actual path replay clears the target. It scans a log-spaced capital grid and bisection-refines the first crossing (plus a second pass to bound non-monotone islands, since replay D_surv is path-dependent). Measures the "capital buffer" the pessimistic static sizing pays for.

oracle_strategy.ml: the strategy-model interface (S signature). A strategy supplies cost_at / fills_for_drawdown / drawdown_of_fills (the funding function), replay (path replay), profit_proxy, and qty floors. The only implementation is Grid, backed by Grid_core (the pure mirror of the live Suicide_grid semantics). The replay accepts an optional seed: the account's current base holdings, base locked in resting sells, and the accumulated profit buffer (from the balance snapshot + accumulated_state.json, via the strategy state). The survival verdict therefore models the strategy as it actually runs: a Hyperliquid grid with accumulated profit can fire its reduced (accumulating) sells, a hypothetical fresh grid never can. The replay anchors the ladder at the path's start (the earliest bar), not today's close. Anchoring at the last close would grind the ladder down through the whole historical range on any uptrend, burning capital on a phantom drawdown. A never-exhausted replay reports d_surv = 1.0 (keeps coverage monotone in capital for the binary searches).

4. The Deployment Engine (oracle_deploy.ml)
This is the core decision. Given a venue-locked capital pool, the asset's blend models, and the config's grid_interval range [lo, hi], it decides: tuned gi, order qty, and whether the asset stays active.

Resolution order (all pure, strategy-generic via the Engine functor):
1. Governing drawdown d_gov: across all horizons, the deepest drawdown whose blended coverage reaches the target (99%). This is the binding horizon for the coverage verification. If no horizon can reach it (a coverage gap), fall back to the deepest drawdown the asset's own history actually observed ("raw" fallback for immature assets, flagged not-authoritative). No MFD windows at all means inactive ("no usable history").
2. Sizing drawdown d_cover: the ATH-scaled survival reference (sizing_reference_of). floor_ref = ATH·(1 − max_drawdown), where max_drawdown is the deepest actual peak-to-valley event (peak_to_valley_stats_of). The ATH is the current regime's top, so "where the price sits relative to the ATH, compared to the worst drop" funds the remainder that is still ahead: d_cover = (price − floor_ref)/price when the price is above the floor. It is 0 at the ATH (the full worst drop is ahead), partway down it is the remainder, and it never exceeds the worst-ever drop, because a maturing asset is not expected to repeat it. At or below the floor ("living in the max drawdown", where the values match, d_from_ath ≈ max_drawdown), or when the deepest event never recovered (the asset is still inside it), the remainder is exhausted: the measured 90th-pct floor overshoot funds the asset instead (0.15 fallback when no floor-break was ever measured). Immature fallback assets keep the raw event drawdown (a floor from a thin history is not a meaningful support). No ATH-to-ATL anchoring: a 1000x run-up only registers the falls that actually happened, never the ATH-to-ATL span, which would read as a phantom 99.9% drawdown.
3. The gi search over the full config range at the minimum order size: the most aggressive (tightest) parameter in [lo, hi] whose deployment reaches 100% replay survival, meaning the replayed path, funded with the pool, never runs dry ("first get 100% survivability at the most aggressive grid_interval(min,max)"). When no parameter can (the pool cannot survive the whole history even at the minimum qty), the sizing stretches: gi = hi with the minimum qty. The widest spacing the config allows stretches the capital's survival as far as possible.
4. The qty: the minimum order size in stretch mode. The order qty only grows to deploy residual capital behind 100% survival, and qty_cap_mult is the ceiling, not a rule (qty_cap_mult ≤ 0 means the qty never grows). In coverage mode it is the largest qty in [qty_min, qty_min × qty_cap_mult] that keeps 100% replay survival, "deploy all capital by adjusting qty", bounded by the survival replay itself (the replay is funded with the pool, so a qty the pool cannot carry exhausts it and fails the criterion by itself). The final row is re-verified at the resolved (gi, qty), so the published D_surv / coverage / deployed reflect the sizing that actually runs.
   The verification replay starts from the account's accumulated state when a seed is provided: held base (the balance snapshot's available base), base locked in resting sells, and the accumulated profit buffer (accumulated_state.json via the strategy state). The grid is modeled as it actually runs, not as a fresh grid. The F&G / range sentiment blend is gone from the sizing: the gi is survival-driven over the config range and the qty follows the "100% first, then deploy residual capital" rule. The F&G value and the weights are still carried in parameter_components for the record (and logged), but they never influence the resolved sizing.

Inactive reasons: no usable history; pool can't fund the first buy at the sizing floor (max(venue qty_min, config qty), never below the configured qty, since a venue qty_min is a lot precision, not a minimum order size) unless a committed resting buy is already in place (the first buy is funded and resting on the exchange; its cost is locked in the account balance, which is why the available pool reads low; the running grid keeps trailing and its own capital gates pause it when the pool cannot extend another rung); or replayed D_surv below --min-active-dsurv.

Fallback mode (immature history): the "raw" observed-drawdown sizing basis and the not-authoritative caveat still apply (thin/gapped history cannot clear the statistical target), but the sizing rules are identical. There is no separate static-funding criterion anymore; 100% replay survival is the only criterion, and an immature asset that reaches it is sized exactly like a mature one.

sizing_floor note: max(min_qty, design_qty). Sizing an order to the raw venue qty_min produces a sub-minimum buy the venue rejects ("cost basis must be ≥ minimal amount").

The tuning surface (tuning_rows) records every candidate row for the report: parameter, qty, deployed, static/replay D_surv, per-horizon coverage, passed, static_funded, profit_proxy.

5. The Live Runtime (oracle_runtime.ml)
Runs the same pipeline continuously inside the engine as a supervisor-managed module (Supervisor.start_oracle; see the intro. The old detached Oracle_runtime.start remains only as a fire-and-forget convenience). Defaults mirror the CLI.

Live-engine data paths: the runtime prefers the engine's in-process websocket-fed mechanisms over the CLI's standalone HTTP calls wherever the semantics match. Whether REST or websocket ("where able") is used is declared per venue by the adapter, not hardcoded here.
- Balances: venue pools come from the live exchange balance stores (websocket-fed by the supervisor, via Exchange_intf.Oracle.S.live_balances) for Kraken/Alpaca, with the REST one-shot fetch as fallback. Hyperliquid declares no live snapshot (the live store mixes perp USDC into "USDC"); its spot-only semantics are REST-authoritative.
- Start price: the grid ladder anchors at the live top-of-book bid (the grid's first order is a resting buy and buys price off the bid, per compute_buy_ref_price's convention) from the websocket orderbook feed, never a mid. The ask backs a missing bid, the last history close is the last resort, and a live price diverging >30% from the close is rejected as stale.
- History: disk-persisted with delta refresh (oracle_cache.ml), the HFT/engine pattern (same data/ + atomic-write convention as State_persistence). Full histories (Kraken's inception walk can be 60 pages, Hyperliquid's candleSnapshot, Yahoo's deep history) are downloaded once per symbol into data/oracle_history/v2/<exchange>/<symbol>.json (v2 = raw bars + read-time normalization; the v1 cache stored already-normalized series and could not self-heal after a rule change). Every later pass loads the cache and only fetches the days it does not cover yet (one small request per asset), or skips the network entirely when the cache is current (last bar covers today/yesterday). A bounded history (the Yahoo deep extension, which only runs to the day before the venue series starts) is complete once its last bar reaches that end date and is then never re-fetched. The cache stores raw bars (the source truth); the shared clean-series normalization (Oracle_calendar.normalize_bars) applies on read, so cache, venue fetch, CLI and replay all see one identical series and a corrected rule self-heals without a refetch. A failed delta falls back to the cached history (stale but real, on top of the last-known-good machinery). Yahoo's walk is mutex-serialized (one request stream at a time) so the parallel pass cannot rate-limit itself on a cold cache.
- Pass concurrency: Phase A analyzes every asset in parallel (Lwt_list.map_p, each asset still individually 60s-bounded). The per-asset oracle latency column reflects the decision path only (see "Background refresh" below): in steady state it is a fingerprint compare, microseconds. Phase B sizing stays strictly sequential per account by design (pool pass-down is order-dependent).
- Committed-capital and open-order state already read the live registry (Exchange_intf).

The CLI (no supervisor, no registry) keeps its pure HTTP paths. This integration is live-run-only.

Engine latency metrics: every pass is profiled (Latency_profiler, histogram windows published at each pass end). That covers engine-global pass / balance / fetch / sizing stages plus one per-asset profiler covering that asset's whole pipeline (analysis + sizing, with the slow stage as max_cause). The refresher records and publishes the balance/fetch windows at each background cycle (so the dashboard shows refresh latency at the balance-reconciliation cadence, not only at pass ends); the pass records and publishes its own pass/sizing windows and the per-asset windows. They are exposed via profiler_snapshots / asset_profiler_snapshots for the dashboard: the latency KPI card shows the oracle pass p50/p99 and the engine latency table's first column shows each domain's per-asset oracle decision latency. In steady state those per-asset rows are microsecond-class (cache-hit / sizing-reuse samples); the ms-class work appears under the balance/fetch rows (background refresh), never in the decision path.

Publication model: one lock-free snapshot, an immutable decision list swapped via a single Atomic.set. Trading domains do an Atomic.get each cycle and adopt qty / grid_interval / active, with case-insensitive lookup by exchange/symbol. Each decision carries parameter_components: the survival-driven resolved gi (fng_parameter is always None, since there is no sentiment blend) plus display reasons (gi_reason / qty_reason) for how the sizing was chosen. Consumers adopt the published sizing and never recompute a competing F&G-only gi. The domain spawner's per-cycle F&G re-evaluation therefore: (a) while the oracle holds a decision, only refreshes accumulation_buffer (which the oracle does not size) and logs the oracle's published sizing (gi/qty reasons + D_surv); (b) only when the oracle has no decision (asset not modeled / analysis failed) applies the F&G-only mapping over the config range, logged explicitly as fallback. One sizing, one owner; the two signals never fight. When the oracle publishes a changed qty/gi, the domain flags the strategy state (force_buy_reanchor) and the buy-trailing leg re-anchors the resting buy to the new sizing target in both directions. Normal trailing only moves the buy up, so without the flag a widened grid interval would leave the whole book running at the old, tighter spacing (buy too close to the market, rungs not 2·gi apart) until the market happened to rise; the flag clears once the buy sits at the target.

Every pass logs one scannable line per asset at INFO, the heartbeat of the decision: "[2/4] hyperliquid/HYPE/USDC ACTIVE | buy 0.5 HYPE every 5.00% | capital $10.06 of $864.27 | drop 61.6% (worst 70.9% 2024-12-21 to 2025-04-07) | survives 9.8% | UNDER-FUNDED". "capital $X of $Y" is the capital the deployment actually consumes of the venue pool (the priority asset is not displayed as absorbing the whole pool). The "drop" is the ATH-scaled remainder actually funded (the full worst drop when the price is at/near the ATH; "floor overshoot" in the at-floor / unrecovered regime). The detail block (drawdown event prices, the funding reference, model horizon, the sizing reasons, the accumulated-state seed, and the committed-buy flag) is logged once and then only when it changes. Problems (under-funded, the 100%-survival gap, coverage gaps, at/below the floor) go to WARN, deduped per asset. History/reservation lines are debug. Steady-state passes are ~10 short lines total, not a wall of text.

Per-asset knobs: the global "oracle" section in config.json can carry an optional "assets" map overriding any sizing/blend/history knob per trading symbol (case-insensitive; a "venue/symbol" key like "hyperliquid/HYPE/USDC" wins over the bare symbol): target_survival, fng_weight, range_weight (both inert, since the sizing is survival-driven; kept for config compatibility), min_active_dsurv, qty_cap_mult, no_deep_history, weight_by_sessions, horizons. Present keys merge onto the global values, absent keys inherit; capital pooling is untouched (still venue-level joint allocation below). Cadence and wait machinery (refresh/poll/max_capital/startup_wait_seconds) stay global. The startup log lists the effective override map and warns on keys matching no tracked symbol.

Two-phase joint allocation per venue account (this is what makes it joint, not per-asset):
- Phase A: analyze every asset first, computing each asset's reservation: the minimum funding to reach its ATH-scaled sizing drawdown (the remaining drop to the expected floor, or the floor overshoot at/below it; raw for fallback assets) at the tightest config gi (ladder cost at the sizing floor + first-buy cost). Informational; the allocation itself never reserves anything for anyone.
- Phase B: allocate sequentially, highest priority first. Each asset sizes against the entire remaining pool (the priority asset is sized fully before the next asset draws anything), and whatever its deployment does not consume passes down the priority order. Nothing is reserved for lower-priority assets, so a capital shortage never starves the priority asset and never lets the least-prioritized asset absorb the pool. With the stretch sizing a priority asset consumes only what its minimum-order ladder needs, so the next asset still funds its own first order. Only a fully funded account idles surplus; fully deployed accounts show ~zero pool (a normal state, "cannot fund the first buy" while awaiting sell fills to restore capital). The pool is venue-locked and the pass-down subtracts each deployment, so pool resources are never double-counted.
- Priority reclamation (oracle_reclaim.ml): when a higher-priority asset fills its last buy and the available pool can no longer fund a replacement while a lower-priority asset still holds committed buy capital, the account is under-deployed in priority order. The runtime computes a per-account reclamation plan fresh every pass (one open-order fold + arithmetic, applied on top of the memoized decisions; not part of the account sizing fingerprint, so constant buy-amends never bust it). The plan selects the fewest lower-priority resting buys, lowest priority first, whose committed capital (remaining_qty × limit price) closes the funding gap, and publishes those assets inactive-with-reclaim (decision fields reclaim_capital / reclaim_target, reason "capital reallocated to <target> (higher priority)"). The domain worker of a reclaimed asset cancels its own resting buy(s) through the normal order pipeline (latched once per reclaim transition); the cancel event returns the committed capital to the available pool and triggers the next pass, which re-sizes the account in priority order and reactivates the priority asset. A lower-priority asset is never reclaimed unless the deallocation actually funds a higher-priority first buy; otherwise it stays active on its committed capital. Candidate scope: any lower-priority asset holding committed buy capital is eligible. Committed capital always flows toward the highest-priority asset that needs it; the plan's conservation objective (fewest cancellations, then lowest priority) keeps disruption minimal.
- Sells are never capital-gated: an asset whose buy placement is halted (pool exhausted, or the oracle INACTIVE) still runs the sell leg. The domain no longer gates the whole execution block on the oracle halt; it passes ~oracle_halted into execute_strategy, which skips only the buy leg (no new buy, no buy trailing/amending). The sell for a just-filled buy is therefore always placed (it needs only inventory, not quote), because it is the account's capital-recovery path, so the last fill's inventory is never left unreclaimable.

Background refresh and the microsecond decision path: the pass (run_pass) performs no network I/O. A separate refresher fiber owns every REST call (balances for all accounts in parallel, history deltas, deep history, class members, fee enrichment once per asset, and the Alpaca calendar refetched at most once per day) and publishes an immutable materialized world state (Atomic swap): per-asset history arrays, per-account pools + balance snapshots, the F&G value. The pass consumes only that state:
- Analysis memoization: each asset's analysis is keyed on its materialized inputs (bars array identity, deep count, members, calendar model, f&g, resolved knobs, grid-relevant config fields). The refresher reuses the same array objects while nothing changed, so a physical `==` compare is the fast path; otherwise an exact full compare (microseconds for a few thousand bars) decides. Unchanged inputs return the same analysis record, so the replay/blend (the 1-2s class-surface work for a crypto_alt-class asset) is not re-run. The live top-of-book anchor is not in the fingerprint: sizing rebuilds the grid ladder from the fresh bid at decision time, so a memoized analysis never pins a stale price.
- Account sizing memoization: sizing is sequential within an account (pass-down), so it is memoized per account on (analysis ids in priority order, pool bucketed to 0.5%, strategy state (accumulated profit / reserved base / venue base, which catches fills exactly), and f&g). An unchanged account re-publishes its previous decisions; only a moved pool/state/analysis re-runs the deployment engine (ms-class).
- Cadence: the refresher cycles at the balance-reconciliation cadence (poll_seconds, 30s) and immediately on fill events; full history refreshes run at the refresh cadence (300s, always on cold start). The pass loop is fully event-driven and never waits on a timer: it wakes on [request_pass], or when a refresh cycle changed analysis-relevant inputs (f&g move, new bars, member/calendar change); balance-only cycles never wake it. A fill-triggered pass sizes against the fill immediately: the domain notifies the runtime with the pool delta (notify_fill / notify_order_cancel) and the pass applies it to the account pool in process, so the decision path never waits for the refresher's authoritative balance (that 5s network wait is gone). The refresher reconciles the authoritative value in the background and its published record supersedes the deltas. For venues with a WS-fed live store (Kraken/Alpaca) the pass reads the store itself at decision time (in-process, no HTTP), so the pool is already event-updated. Fetch failures (the 10s-timeout class) happen in the background with exponential backoff (30s, capping at 300s), never on the decision path.
- Event-driven wakes: the engine calls request_pass (one Atomic increment + an Lwt_condition broadcast, microsecond-scale, from the domain worker loop) on every fill and canceled/rejected/expired order; both loops wake on the condition immediately, with no 50ms polling slices and no 2s minimum gap. Bursts of events coalesce because one pass drains the whole pool-delta queue, and the account sizing memo cache turns an unchanged account into a microsecond re-publish.
- Cold start: the refresher cold-fetches histories in the background while the pass loop publishes nothing ("first background refresh still in progress"); when the first materialized state lands (history changed, pass woken), the first real decisions publish, with the same time-to-first-decision as the old inline cold pass and the engine never blocked meanwhile. The cold-start pass does not count as a "pass attempt" for the domain startup gate (pass_attempts increments only when a pass actually reaches the decision phase): if it did, the domains' F&G-only fallback would open while the first real decisions are still seconds away and place capital-unaware orders the first real pass immediately declares INACTIVE (exchange-rejected for insufficient funds). The startup deadline (startup_wait_seconds, default 60) remains the escape hatch when the refresher can never materialize (sick upstream).
- Event-driven passes: the engine calls request_pass (one Atomic increment plus an Lwt_condition broadcast, microsecond-scale) on every fill and canceled/rejected/expired order; the loops wake immediately on the condition, with no 50ms polling slices and no 2s minimum-trigger gap. A fill/cancel also enqueues its pool delta (notify_fill / notify_order_cancel), which the pass applies to the account pool in process so the decision path never waits on a network balance refresh; the refresher reconciles the authoritative value in the background. Bursts coalesce through the single queue drain per pass and the account-sizing memo cache.
- Failure semantics, last-known-good: an asset whose analysis fails or times out (each asset's analysis is bounded at 60s; every fetch is timeout-guarded) keeps its previous decision; an account whose balance can't be fetched is skipped entirely; an entirely failed pass publishes nothing and the runtime never crashes the engine. publish merges fresh decisions over the old snapshot, so a partial pass never halts trading.
- Deepening and members: each asset's venue series is extended with Yahoo deep history (unless disabled; pre-listing windows are skipped and the empty prefix cached, so a recently-listed asset is never re-requested). Class members are blend inputs, never decision subjects, so they gather their price history purely from Yahoo (whitelisted symbols only; dead-token collisions like HYPE/BNB are skipped, not fetched), unless the member is the active asset on the exchange itself, which uses the exchange's own history (it is the decision subject and needs venue data). Members are disk-cached with the same delta policy (yahoo-class keys) and Yahoo walks are mutex-serialized and globally paced (~2 req/s) so the refresher cannot throttle itself. The oracle never probes alt coins on venues that do not list them (no more per-pass Hyperliquid "no spot history" warning spam for class members). Alpaca gets a real market-calendar model; failures fall back to business weekdays. F&G is resolved (live index, cached, None on failure, never a fabricated sentiment value); the sizing itself no longer blends it (survival-driven), and the domain spawner still uses it as the fallback sizing when the oracle holds no decision.

Warnings are deduped per asset (log once on change, then debug), since the oracle re-derives the same "under-funded" warnings every pass.

6. Portfolio Mode (legacy --portfolio)
oracle_topology.ml: qualified instrument identity (venue/symbol/base/quote/testnet), topology JSON parsing/validation, transfers (SESSION:FROM->TO=AMOUNT), timeline alignment without forward-filling.
oracle_portfolio.ml: a multi-asset replay. Capital is pooled per venue account (venue + quote + testnet), never per asset, never system-wide. All positions on a venue draw from one shared pool (a cash_hook into Grid_core), so a sibling's buy starves your grid too; the venue's survival is the pool's survival. Transfers move budget between venue pools at session boundaries; troughs track the actual joint pool minimum.
oracle_portfolio_state.ml: persistence (--positions-file / --save-positions): pool/base per qualified key, atomic write (tmp + rename).

7. The CLI (bin/oracle.ml)
Usage: dio-oracle [SYMBOL] [options]; with no symbol, analyzes every config.json trading asset on its own exchange, grouped by venue account, in config priority order, threading remaining pool down. Key modes:
- Per-asset analysis: fetches fees, then the series, deepens, loads class members, runs analysis, builds blend models, then deploy_asset (the sizing replay is seeded with the asset's accumulated state: reserved base + accumulated profit from accumulated_state.json via the strategy state), followed by supporting analysis (replay at the deployment's sizing, per-horizon path coverage, static min capital, max qty, empirical min capital with buffer ratio).
- --portfolio / --topology / --allocation / --transfer: the venue-pooled portfolio replay with capital assignment rules (explicit allocations win; --total-capital splits; else live balances; 1000 offline).
- --from-csv / --from-json: offline mode, single asset, no network.
- --json: machine-readable report.
- Notable knobs: --capital, --target-survival, --fng (display), --fng-weight / --range-weight (inert, since sizing is survival-driven), --min-active-dsurv, --qty-cap-mult (the qty ceiling, not a rule), --kappa / --class / --members, --horizons / --thresholds / --percentiles, --gap-tolerance, --vol-window, --no-deep-history, --max-capital, per-venue gates (--qty-min, --min-notional, increments).

Key Design Invariants (worth internalizing)
 1. Never forward-fill. Gaps are metadata; analysis refuses when max_gap > tolerance.
 2. No lookahead. Trailing volatility at start s uses only bars ≤ s.
 3. Non-overlapping windows for the tail. A single contiguous crash is counted once; n_eff is the honest sample size.
 4. Empty distributions raise, never return 0. 0.0 from zero observations would masquerade as "never drew down".
 5. The blend is a true weighted average on one window basis. Sigma=0 starts are excluded from both sides; n_asset = effective window count so κ is a real pseudocount.
 6. Coverage functions are monotone, so bisection is sound; replay D_surv is not monotone in capital, so empirical sizing uses scan-and-refine.
 7. The sizing drawdown is the ATH-scaled remaining drop to the expected floor (ATH·(1 − deepest actual peak-to-valley drawdown)), "where the price sits relative to the ATH, compared to the worst drop", capped by the worst-ever drop, and replaced by the measured floor overshoot at/below the floor or when the deepest event never recovered. Never an ATH-to-ATL construction (a 1000x run-up must not read as a 99.9% drawdown); immature fallback assets keep the raw event drawdown.
 8. 100% survivability first. The gi is the most aggressive config value that survives the whole replayed history at the minimum order size; the qty only grows behind 100% survival, and qty_cap_mult is the ceiling, not a rule. When 100% is unreachable, the sizing stretches (minimum qty at the gi maximum).
 9. Verification is funded with the actual pool budget and starts from the account's accumulated state. The honest survival question: "can THIS grid, as it actually runs, survive this history with the capital it's entitled to?" Static cost would under-state a long path's burn; a fresh grid would under-state a running one's ability to sell.
10. The sizing respects committed capital. An asset with a resting buy on the exchange is never "cannot fund the first buy" (the first buy is already funded and locked in the balance); the running grid keeps trailing, and its own capital gates pause it when the pool cannot extend another rung. The reclamation pass is the one exception to committed-capital protection: any lower-priority committed grid is canceled, only when its release actually funds a higher-priority asset that cannot fund its own first buy after a fill. The conservation objective (fewest cancellations, then lowest priority) is what keeps the disruption minimal, not a funded-ness filter.
11. Failure = last-known-good everywhere. The runtime degrades gracefully, never crashes the engine; every fetch is timeout-bounded, runs in the background refresher with exponential backoff, and each asset's analysis is capped at 60s, so one hung upstream can never hang the trading system.

A few observations from the review (not bugs, but worth knowing):
- Kappa defaults differ slightly by context: Oracle_archetypes says 365/252, but the runtime and CLI fall back to 200 when config has no per-class kappa (config.json "classes" entries override).
- The runtime and CLI duplicate a fair amount of pipeline code (analyze/size logic appears in both bin/oracle.ml run_one and oracle_runtime.ml analyze_asset/size_asset); the runtime's version is the maintained one and the CLI's is largely parallel. The data pipeline (fetch series, Yahoo deep history, class members, equity calendar) is unified in oracle_fetch.ml.
